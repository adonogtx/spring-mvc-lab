# spring-mvc-lab

A hands on Spring MVC lab. The goal is to **see in action** every part of an HTTP request and response inside a Spring Boot application: path, query string, headers, body, status, the difference between `@Controller` and `@RestController`, the difference between returning an object directly or returning a `ResponseEntity`, and the difference between `PUT` and `PATCH`.

The domain is **Fuji Mart**, a fictional konbini chain with a few stores, each selling its own products. It is deliberately simple: pure CRUD with almost no business logic, so all the attention goes to how Spring maps HTTP to Java and back.

| Part of the request | Use in the domain |
|---|---|
| path | store id, product id |
| query string | filters such as category, max price, in stock, sorting |
| headers | response language, staff identifier, correlation id |
| body | the data for a new or updated product |

## Main rule

**Before every request, write down your prediction** of the status, the relevant headers and the body. Only then send it. The gap between prediction and result is where the learning happens. Wrong predictions are the most valuable ones: record what you expected.

Looking up API names and syntax is allowed. Copying a tutorial line by line does not count.

## API overview

By the end of the lab, the API looks like this:

| Operation | Method and path | Main concepts |
|---|---|---|
| list stores | `GET /v1/stores` | basics |
| get store | `GET /v1/stores/{storeId}` | path, 404 |
| list a store's products | `GET /v1/stores/{storeId}/products` | query params |
| get product | `GET /v1/stores/{storeId}/products/{productId}` | two path variables, headers, conditional header |
| get product, no `ResponseEntity` | `GET /v1/stores/{storeId}/products/{productId}/simple` | default 200, 404 without `ResponseEntity` |
| create product | `POST /v1/stores/{storeId}/products` | body, required header, 201 with `Location` |
| replace product | `PUT /v1/stores/{storeId}/products/{productId}` | full replacement, idempotence |
| partially update product | `PATCH /v1/stores/{storeId}/products/{productId}` | partial update |
| delete product | `DELETE /v1/stores/{storeId}/products/{productId}` | 204, `ResponseEntity<Void>` |
| delete product, no `ResponseEntity` | `DELETE /v2/stores/{storeId}/products/{productId}` | 204 with `void` |

Plus the lab only endpoints under `/lab` (Parts 1 and 2).

## Postman setup

### Organization

- Create a **Collection** named `spring-mvc-lab`, with one folder per part (`part_1_echo`, `part_2_controller`, `part_3_path`...).
- Save each request with a name that describes the scenario, for example `GET store id abc`. By the end, the whole lab can be rerun.
- Create an **Environment** with the variable `baseUrl = http://localhost:8080` and write URLs as `{{baseUrl}}/v1/stores/1`.

### Where to build each part of the request

| HTTP part | Where in Postman |
|---|---|
| method | dropdown to the left of the URL |
| path | the URL itself |
| query string | **Params** tab (the checkbox toggles each param on and off) |
| headers | request **Headers** tab |
| body | **Body** tab, **raw** option, type in the dropdown next to it (JSON, Text...) |

### Where to read the response

| HTTP part | Where to look |
|---|---|
| status | top right corner of the response area |
| response headers | **Headers** tab of the **response** (not the request one) |
| body | **Body** tab of the response |

### The Console

Open the **Postman Console** ("Console" icon in the bottom bar). It shows the request **exactly as it was sent**, with every header. Use it whenever the lab asks you to compare what was sent.

Postman **adds headers on its own**. In the request Headers tab, click **hidden** to see them: `User-Agent`, `Accept`, `Host` and, when the body is raw JSON, an automatic `Content-Type: application/json`.

## Part 1: anatomy of a request (the echo)

This part exists to make it obvious where each piece of the request comes from.

### Task 1.1

Create `POST /lab/echo/{segment}` that receives **all at once**:

- the `segment` from the path
- a query param `q`
- the headers `User-Agent` and `X-Request-Id`
- a JSON body (a record with a single `message` field is enough)
- the HTTP method and the full path

Investigation hint: there is an object from the Servlet API that represents the whole request, and Spring can inject it as a method parameter.

The response must be JSON that **says where each value came from**. The exact shape is up to you, but something along these lines:

```json
{
  "method": "...",
  "fullPath": "...",
  "fromPath": { "segment": "..." },
  "fromQuery": { "q": "..." },
  "fromHeaders": { "userAgent": "...", "requestId": "..." },
  "fromBody": { "message": "..." }
}
```

Send it from Postman with everything filled in and compare, line by line, what the **Console** shows was sent with what your endpoint returned. Notice that you never typed `User-Agent`, yet it arrived.

### Task 1.2

Create `POST /lab/echo2/{segment}` that receives **a single parameter** of type `RequestEntity<String>` and extracts the method, URL, headers and body from it.

### Questions

1. Which annotation read each part? Build a list of "part of the request → annotation".
2. How is `RequestEntity` related to `ResponseEntity`?
3. Why do people usually prefer separate annotations over `RequestEntity`?
4. Send `/lab/echo` without the `X-Request-Id` header. What happens? How do you make it optional?

## Part 5: incoming and outgoing headers

### Task

In `GET /v1/stores/{storeId}/products/{productId}`:

- Read the `Accept-Language` header. If it is `ja`, the `name` field in the response must hold the value of `nameJa`. Any other value, or no header at all, returns the English name.
- Read the `X-Request-Id` header as **optional**. If present, return the same value in an `X-Request-Id` header on the **response**. If absent, generate one (a UUID is fine) and return it.

The second behavior is a real industry pattern called a **correlation id**, used to trace the same request across logs.

| Headers sent | Prediction | Actual result |
|---|---|---|
| no extra headers | | |
| `Accept-Language: ja` | | |
| `Accept-Language: en` | | |
| `X-Request-Id: kiryu-001` | | |
| both together | | |

### Questions

1. Why does language make sense as a header rather than a query param or a path segment? There is a defensible argument for more than one side; defend yours.
2. What is the difference between the header you **read** and the header you **wrote**? Which tools did you use on each side?

## Part 8: PUT vs PATCH

### Task

Both on `/v1/stores/{storeId}/products/{productId}`, both requiring `X-Staff-Id`:

| Method | Body | Semantics |
|---|---|---|
| `PUT` | all fields: `name`, `nameJa`, `category`, `priceYen`, `stock` | **replaces** the product with what was sent |
| `PATCH` | any subset of the fields | **changes only** the fields that were sent |

Decide what each one returns on success, `200` with the updated product or `204` with no body, and be ready to justify the choice.

| Scenario | Prediction | Actual result |
|---|---|---|
| `PUT` with every field | | |
| the same `PUT` sent a second time | | |
| `PUT` without `priceYen` in the body | | |
| `PATCH` with only `stock` | | |
| `PATCH` with only `priceYen` and `name` | | |
| `PATCH` with an empty body `{}` | | |
| `PATCH` with `"stock": null` | | |
| `PUT` on product 999 | | |
| `PATCH` without `X-Staff-Id` | | |

After each request, `GET` the product to confirm its real state. Do not trust the response alone.

### Questions

1. What happened to `priceYen` in the `PUT` without that field? Is that a bug, or exactly what `PUT` means?
2. In your `PATCH` DTO, how did you tell "the field was not sent" apart from "a field the client wants to keep"? What types did you have to use, and why does `int` not work there?
3. `PATCH` with `"stock": null`: should it be rejected, ignored, or clear the value? There is no single answer; pick one and defend it.
4. `PUT` is idempotent. Prove it with the requests above. Then design (just describe, no need to build) a `PATCH` body that is **not** idempotent.
5. `PUT` on a product that does not exist: some APIs return 404, others create the resource. When does each choice make sense?
