# spring-mvc-lab

A hands on Spring MVC lab. The goal is to **see in action** every part of an HTTP request and response inside a Spring Boot application: path, query string, headers, body, status, the difference between `@Controller` and `@RestController`, the difference between returning an object directly or returning a `ResponseEntity`, and the difference between `PUT` and `PATCH`.

The domain is **Fuji Mart**, a fictional konbini chain with a few stores, each selling its own products. It is deliberately simple: pure CRUD with almost no business logic, so all the attention goes to how Spring maps HTTP to Java and back.

| Part of the request | Use in the domain |
|---|---|
| path | store id, product id |
| query string | filters such as category, max price, in stock, sorting |
| headers | response language, staff identifier, correlation id |
| body | the data for a new or updated product |

## Main rule

**Before every request, write down your prediction** of the status, the relevant headers and the body. Only then send it. The gap between prediction and result is where the learning happens. Wrong predictions are the most valuable ones: record what you expected.

Looking up API names and syntax is allowed. Copying a tutorial line by line does not count.

## Workflow

Every part follows the same cycle, based on **GitHub Flow**:

```bash
git switch main
git pull
git switch -c feat/part-1-path          # one branch per part
# ... code, commit as often as you want
git push -u origin feat/part-1-path
# open a Pull Request on GitHub, get it reviewed, merge it
git switch main
git pull
git branch -d feat/part-1-path          # the branch is only a label; the commits now live in main
```

Rules:

1. `main` always compiles and passes `./mvnw test`.

## Part 0: domain and seed data

**Goal:** the fake database exists and is populated. No HTTP yet.

### What goes in this branch

| File | Must have |
|---|---|
| `Store.java` | the 5 fields from the domain table |
| `Product.java` | the 7 fields from the domain table |
| `StoreRepository.java` | a Spring bean holding the 3 stores; `findAll()` and `findById()` |
| `ProductRepository.java` | a Spring bean holding the 15 products; `findAll()` and `findById()` |

Nothing else: no controllers, services, DTOs or mappers. Later parts add the repository methods they need (find by store, save, update, delete).

### Decisions

There is no single right answer for these. Pick one and write a one or two line justification for each in the PR description.

1. **Mutability.** Will `Store` and `Product` have setters, or be immutable? Stores are never changed in this lab. Products are changed in Part 7.
2. **Storage.** `List` or `Map` keyed by id? Think about what each one promises about order, and how `findById` works on each.
3. **Loading.** Where is the seed data loaded: constructor, field initializer, instance initializer block? Is the collection `static` or not? Remember that a Spring bean is a singleton by default.
4. **`findById` return type.** What does it return when the id does not exist? Later parts depend on this to answer 404.

### Done when

| Check | |
|---|---|
| data matches the tables exactly, field by field, in the same order | |
| `findAll()` does not let a caller modify the repository's internal collection | |
| `./mvnw test` passes | |
| PR description has the four decisions with justifications | |

### Question

`findAll()` returns a copy of the list. Does that copy protect the data completely? What would happen if a caller changed a field of one of the objects inside it, and how does your answer to decision 1 affect that?

## Part 3: incoming and outgoing headers

### What goes in this branch

Changes to `GET /v1/stores/{storeId}/products/{productId}`.

### Task

- Read the `Accept-Language` header. If it is `ja`, the `name` field in the response must hold the value of `nameJa`. Any other value, or no header at all, returns the English name.
- Read the `X-Request-Id` header as **optional**. If present, return the same value in an `X-Request-Id` header on the **response**. If absent, generate one (a UUID is fine) and return it.

The second behavior is a real industry pattern called a **correlation id**, used to trace the same request across logs.

| Headers sent | Prediction | Actual result |
|---|---|---|
| no extra headers | | |
| `Accept-Language: ja` | | |
| `Accept-Language: ja-JP` | | |
| `Accept-Language: en` | | |
| `X-Request-Id: kiryu-001` | | |
| `Accept-Language: ja` and `X-Request-Id: kiryu-001` | | |

### Questions

1. Did `ja-JP` behave like `ja`? Should it? (`ja` is a language, `JP` is a country, like `pt` and `BR` in `pt-BR`.)
2. Why does language make sense as a header rather than a query param or a path segment? There is a defensible argument for more than one side; defend yours.
3. What is the difference between the header you **read** and the header you **wrote**? Which tools did you use on each side?

## Part 7: PUT vs PATCH

### What goes in this branch

`PUT` and `PATCH` on `/v1/stores/{storeId}/products/{productId}`, both requiring `X-Staff-Id`, their request DTOs, and an update in the repository.

### Task

| Method | Body | Semantics |
|---|---|---|
| `PUT` | all fields: `name`, `nameJa`, `category`, `priceYen`, `stock` | **replaces** the product with what was sent |
| `PATCH` | any subset of the fields | **changes only** the fields that were sent |

Decide what each one returns on success, `200` with the updated product or `204` with no body, and be ready to justify the choice.

| Scenario | Prediction | Actual result |
|---|---|---|
| `PUT` with every field | | |
| the same `PUT` sent a second time | | |
| `PUT` without `priceYen` in the body | | |
| `PATCH` with only `stock` | | |
| `PATCH` with only `priceYen` and `name` | | |
| `PATCH` with an empty body `{}` | | |
| `PATCH` with `"stock": null` | | |
| `PUT` on product 999 | | |
| `PATCH` without `X-Staff-Id` | | |

After each request, `GET` the product to confirm its real state. Do not trust the response alone.

### Questions

1. What happened to `priceYen` in the `PUT` without that field? Is that a bug, or exactly what `PUT` means?
2. In your `PATCH` DTO, how did you tell "the field was not sent" apart from "a value the client wants"? What types did you have to use, and why does `int` not work there?

5. `PUT` on a product that does not exist: some APIs return 404, others create the resource. When does each choice make sense?
6. How did your mutability decision from Part 0 affect the implementation of the update?

## Part 9: the whole request at once (the echo)

**Goal:** you have read every part of a request separately. Now read them all in one place.

### What goes in this branch

`EchoController` in the `lab` package.

### Task 9.1

Create `POST /lab/echo/{segment}` that receives **all at once**:

- the `segment` from the path
- a query param `q`
- the headers `User-Agent` and `X-Request-Id`
- a JSON body (a record with a single `message` field is enough)
- the HTTP method and the full path

Investigation hint: there is an object from the Servlet API that represents the whole request, and Spring can inject it as a method parameter.

The response must be JSON that **says where each value came from**. The exact shape is up to you, but something along these lines:

```json
{
  "method": "...",
  "fullPath": "...",
  "fromPath": { "segment": "..." },
  "fromQuery": { "q": "..." },
  "fromHeaders": { "userAgent": "...", "requestId": "..." },
  "fromBody": { "message": "..." }
}
```
